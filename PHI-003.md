# 🎣 PHI-003 — Spoofed Identity: Gibberish Domain Infrastructure

> **Path:** Phishing-Investigations / PHI-003

---

## 🧠 What This Investigation Is About

A suspicious email arrived with a sender address built from a string of random alphanumeric characters — the kind of domain that no real organization would ever use. The sending IP traced back to Microsoft's cloud infrastructure, a deliberate choice to borrow legitimacy from a trusted provider. The complaint path routed through an Italian server with no clear connection to any of the other domains involved.

The attached link pointed to `kyempapu.org` — flagged suspicious by security vendors and carrying an active reputation for malicious behavior across threat intelligence sources, despite appearing relatively clean on VirusTotal's engine count.

This investigation demonstrates how fabricated sender infrastructure combined with trusted cloud IPs and low-detection payloads is used to slip past automated defenses.

**Verdict: True Positive — Escalated to L2 SOC**

## 🎯 SOC Relevance

This investigation highlights a technique where attackers deliberately construct **disposable, unresolvable sender domains** — random strings that cannot be traced, reported, or blocked by domain reputation alone. Paired with a **trusted cloud IP** from a provider like Microsoft Azure, the email bypasses IP-based blocking while the nonsense domain ensures the infrastructure can be rotated freely at zero cost.

The broader lesson for SOC analysts is that **detection cannot rely on any single signal**. A clean IP, a low VT detection count, and a new domain each tell one part of a story. The analyst's job is to read all the signals together — and this case is a strong example of how that multi-signal approach reveals what any single check would miss.

## 🔍 Investigation Walkthrough

### Step 1 — Header Extraction (MXToolbox)

Pulled the full email header through MXToolbox to assess authentication and routing.

**Authentication results:**

| Check | Result |
|-------|--------|
| SPF | ❌ None |
| DKIM | ❌ None |
| DMARC | ❌ None |

> Complete absence of all three authentication mechanisms. No legitimate sender — individual, business, or service — operating at any scale skips SPF, DKIM, and DMARC simultaneously. This alone places the email in the suspicious category before any other analysis begins.

### Step 2 — Sender IP Analysis (AbuseIPDB + VirusTotal)

Looked up the originating IP `51.104.208.151`.

**Findings:**
- **ISP:** Microsoft Limited
- **AbuseIPDB:** No reports
- **VirusTotal:** Unrated

📸 `[SCREENSHOT — AbuseIPDB result for 51.104.208.151 showing Microsoft as ISP]`

> Microsoft Azure IP addresses are used by millions of legitimate services every day, which is precisely why attackers provision sending infrastructure there. The IP carries built-in trust that reputation-based filters are reluctant to block. An unrated, clean Microsoft IP combined with zero email authentication is the classic setup for a campaign trying to ride trusted infrastructure through the front door.

---

### Step 3 — Sender Domain Analysis

Investigated both sender domains: `8DDW299YD3LSARPE5KWZZCHBHC2B.com` and `A8XINU8B9JL9H1.com`

**Finding: Neither domain is real.**

Both domains are constructed from random alphanumeric strings with no connection to any registered entity, business, or service. Domains of this structure exist for one purpose: **single-use disposable sending infrastructure**. They are registered cheaply, used for one campaign, and abandoned before they accumulate reputation flags.


> Real organizations — even small ones — use recognizable, meaningful domain names. A sender domain that looks like a randomly generated password is an immediate red flag, regardless of what the email says or how legitimate the IP looks.

---

### Step 4 — Routing Anomaly: Complaint Path

The email header included a complaint address routing to `we16.morona.it` — an Italian server with no connection to any of the other domains involved in this email.

> Complaint-to routing through an unrelated third-country server is a sign of infrastructure stitched together from multiple disposable components. Legitimate bulk senders route abuse complaints to their own domain. An Italian complaint server appearing in an email with US cloud infrastructure and nonsense domains indicates this campaign was assembled from separate pieces — a common pattern in spam-as-a-service operations.

---

### Step 5 — URL Analysis (VirusTotal + Threat Intelligence)

Submitted the attached link `https://kyempapu.org` to VirusTotal.

**VirusTotal result:** Flagged suspicious by **ESET** engine only — low detection count.

📸 `[SCREENSHOT — VirusTotal result for kyempapu.org showing ESET detection]`

> A single engine detection does not mean the link is safe. `kyempapu.org` carries an active suspicious reputation across independent threat intelligence sources — security provider warnings, potential malware or phishing blacklist appearances, and minimal legitimate footprint. Low VT detection counts are common for freshly deployed or recently rotated malicious infrastructure that hasn't been widely reported yet. The domain's broader threat intelligence profile, combined with every other indicator in this email, is sufficient to treat this link as malicious pending sandbox confirmation.

## 📋 Key Takeaways

- **Gibberish domains are an automatic red flag.** No legitimate sender uses randomly generated alphanumeric strings as a domain name. Recognizing this pattern on sight — before running any tools — is a fast, reliable first-pass filter that costs zero time.
- **Trusted ISP ≠ trusted sender.** Microsoft, Google, and Amazon cloud IPs appear in phishing campaigns regularly because attackers know these ranges are rarely blocked. Seeing a major cloud provider as the ISP should prompt more scrutiny, not less — it means the attacker is trying to borrow credibility.
- **Low VT detection count is not a clearance.** One engine flagging a domain while 70+ others pass it clean can mean the payload is new, recently rotated, or specifically crafted to evade signature-based detection. When the rest of the email is already suspicious, a low-detection URL needs sandbox analysis — not a pass.
